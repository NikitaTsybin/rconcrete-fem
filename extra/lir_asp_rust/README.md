# Экспериментальный Rust-парсер LIR + ASP

Отдельный crate. Rconcrete FEM использует `read_model` для восстановления расчётной схемы из LIR. Нативный Rconcrete Grid использует собственную копию этого пакета для импорта LIR и ASP. Библиотека принимает байты ASP и `Read + Seek` для LIR. В качестве источника подходит файл на диске или `Cursor<&[u8]>` в памяти.

Основание формата — JavaScript-парсер и его тесты в `C:/web/grid/web`, а также наблюдения в `docs/lir_asp_reference` проекта FEM. Поддерживаются исследованные LIR с однобайтовой длиной заголовка, FileAnsiCP/Preview/MetaDataN и завершающими NUL (в том числе варианты 2024/2026), ASP ARM-SAPFIR_5 (определения 88 байт) и ARM-SAPFIR_6 (120 байт). Неизвестные варианты отклоняются.

## API

```rust
use lir_asp_parser::{import_pair, Unit};
use std::io::Cursor;
let mut input = Cursor::new(lir_bytes);
let result = import_pair(&mut input, asp_bytes, Unit::Meters)?;
```

Этапы доступны отдельно: `parse_asp`, `read_lir_subset`, `match_plates`, `select_all`. Ошибки возвращаются как `Result<T, String>`; сообщения сейчас английские для отдельного исследовательского модуля. ID элементов/узлов на выходе 1-based. Угол осей и As не пересчитываются.

`Selection.plates`: ID, отметка Z и периметр XY в мм; `source` содержит исходные номера узлов, XYZ в единицах входа, проверенный периметр LIR в порядке ASP, направление ASP, все четыре исходных As, внутренний индекс определения LIR. As сохраняются в единицах ASP (см²/п.м). Отрицательное As означает отсутствие результата, ноль допустим. Пластина сохраняется, если хотя бы одна компонента неотрицательна. Отбрасываются негоризонтальные пластины: разброс Z >0.01 мм. Полностью пустая выборка — ошибка. Счётчики пропусков возвращаются отдельно.

Соответствие LIR/ASP проверяется по ID и всем вершинам после f64→f32 (как текущий JS). Сохраняются исходная связность LIR и порядок периметра ASP. Разные топологии одного внутреннего определения отклоняются. Полный словарь типов LIR не декодирован. Геометрия без записей в ASP не удерживается: только выбранные элементы и связанные узлы; соседние чтения объединяются (разрыв до4096 байт, буфер до1МиБ). Вход ASP передаётся целиком, его пластины временно сохраняются для проверки; глобальная геометрия LIR не материализуется.

Стержни ASP структурно проверяются, включая максимумы подробных строк, но не импортируются в 2D. Неизвестный хвост ASP учитывается в диагностике. Трещины, поперечная арматура, служебные определения и удалённые записи выбранной геометрии не импортируются. Неиспользуемые записи LIR намеренно не проверяются, как в текущем разреженном JS-импорте.

## Проверки и последующее сравнение

Из папки crate:

```powershell
cargo fmt --check
cargo test --offline
cargo build --release --offline
# Отдельная проверка компилируемости библиотеки для будущего web:
cargo check --lib --target wasm32-unknown-unknown --offline
# JSON результата в файл; время каждого прохода в stderr:
./target/release/lir_asp_parser.exe model.lir results.asp m 5 > result.json
```

Скрипты `compare.mjs` и `bench_js.mjs` работают из `C:/web/grid/extra/lir_asp_rust`, где им доступен JavaScript-парсер Grid. Для сравнения передайте `compare.mjs` путь к собранному EXE Rust-парсера, пути к LIR и ASP и единицы.

CLI не модифицирует исходные файлы. Парсинг/проверки/выборка измеряются вместе; чтение ASP с диска и JSON-сериализация исключены из таймера, разреженное чтение LIR включено. Каждый повтор заново строит результат, не усредняет предыдущие результаты. Это диагностический инструмент, не обещание ускорения. `compare.mjs` сравнивает значения/геометрию/связность/пропуски точно; это проверка корректности, не бенчмарк: Node предварительно загружает файлы в память.

Остальные реальные пары разных версий и скорость в браузере требуется проверить отдельно. Для честного сравнения позже нужны release Rust/WASM и текущий JS в одном браузере/worker, одинаковые данные и стратегия чтения; отдельно время I/O, декодирования, передачи результата и создания Dataset. Различия native vs browser и прогретый файловый кеш нельзя выдавать за ускорение парсера. Браузерное приложение использует прежний JS; нативный импорт использует эту Rust-библиотеку. Синтетические тесты охватывают заголовки, ASP5/6, разреженную геометрию, проверку координат и As, повреждённые данные и сводки стержней.


## Проверенная реальная пара (23.10.2026)

`vtr_stlb_эксплуатац и кран_2026-10-09_500.lir/.asp` из Downloads/Telegram Desktop: LIR 81 156 912 байт, ASP 3 575 856 байт, ARM-SAPFIR_6. В LIR114309 узлов/161823 записей элементов, удержано19134 узла/19810 пластин; пропусков нет. compare.mjs прошёл точное сравнение всех19810 пластин с актуальным JS: координаты/отметки/связность/направления/As1–As4/индексы определений/счётчики.

Диагностические7последовательных проходов без фоновой сборки, первая попытка исключена из медианы: native Rust release165.4мс, текущий JS в Node494.8мс (~3раза). Это разные среды: Rust читает разреженный LIR через File, JS — Blob из заранее загруженного файла; ASP чтение и выходная JSON-сериализация не включены. Это НЕ замер WASM в браузере и не обещание ускорения всего импорта. Времена зависят от кеша/нагрузки; сырые отчёты в корневом target/lir_asp_{js_perf.json,rust_perf.txt}. bench_js.mjs — воспроизводимый Node-замер. Это исторический замер до подключения парсера к нативному приложению; браузерная версия остаётся на JS.

## 04.11.2026 — геометрия LIR без ASP
Добавлен read_model(&[u8]) для пилотного восстановления FEM. Он сохраняет исходные номера, пропускает записи с флагом0 и определяет топологию по дополнительным записям с типом КЭ/числом узлов, сверяя ID, связность и исходный индекс группы. Если отдельная граничная запись не найдена, тип разрешён только при единственном подтверждённом типе всей группы файла, число таких случаев возвращается отдельно. Глобальная таблица definition_index→type не зашита. Распознаются исследованные изотропные жёсткости типа36 (E,ν,h в см, вес), с проверкой групп/счётчиков/маркера/диапазонов. Это не универсальный декодер LIR. Геометрические и силовые единицы задаёт вызывающий код. Существующий импорт Grid LIR+ASP не менялся. Реальный файл «Модель для импорта.lir»:88717 узлов,138860 действующих КЭ,16315 отключённых,2 типа граничных записей восстановлены по однозначной группе, две жёсткости распознаны.
