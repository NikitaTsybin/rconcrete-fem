# Чтение ASP и извлечение огибающей армирования

## Назначение и границы

Пользователь сам экспортирует ASP из ЛИРА и сам выбирает файл. Это отдельный
снимок результатов, не автоматическое чтение текущего расчёта из LIR.
Требуется экспортировать только огибающие по элементам, без подробных строк.

Проверен формат с сигнатурой `ARM-SAPFIR_5 binary v.5.0 2015`. Все числа ниже
little-endian, координаты и результаты — f32. Строки — Windows-1251,
фиксированной длины, до первого NUL; не UTF-8.

Имена и физический смысл части полей установлены эмпирически по одной модели,
не по официальному SDK. Не объявлять чтение полного подбора армирования:
дополнительные блоки и часть метаданных остаются нерасшифрованными.

## Заголовок — 272 байта

| Смещение | Размер | Содержание |
|---:|---:|---|
| 0 | 32 | NUL-terminated ASCII сигнатура |
| 32 | 64 | Наименование норм, Windows-1251 |
| 96 | 4 | u32: число пластин |
| 100 | 4 | u32: размер записи пластины, ожидается 156 |
| 104 | 64 | Вид результатов, в примере «РСУ» |
| 168 | 72 | Имя варианта |
| 240 | 4 | u32: число записей блока определений |
| 244 | 4 | u32: размер записи этого блока, ожидается 88 |
| 248 | 4 | Неинтерпретированное поле |
| 252 | 4 | u32: число стержневых объектов |
| 256 | 4 | u32: размер постоянной части стержня, ожидается 160 |
| 260..271 | 12 | Неинтерпретированные поля |

В контрольном файле: 125301 пластина, 264 записи определений, 202 стержня,
1860 подробных строк, нерасшифрованный хвост 3048530 байт.

## Порядок блоков

```text
header = [0..272)
plates_start = 272
definitions_start = plates_start + plate_count * 156
bars_start = definitions_start + definition_count * 88

// Для каждого стержня o — начало его записи:
row_count = u32(o + 156)
next_bar = o + 160 + row_count * 44
```

**Нельзя** вычислять `bars_start + i*160`: у стержней переменная длина.
В конце остаётся нерасшифрованный хвост; его наличие не означает ошибку чтения.
Предел `row_count <= 100000` в исходном коде — защитное ограничение, не спецификация.
Проверять каждый размер и смещение до чтения/выделения памяти.

## Пластина — 156 байт

| Смещение внутри | Тип/размер | Поле |
|---:|---|---|
| +0 | u32 | Исходный номер КЭ с нуля; для примера `element_id=raw+1` |
| +4 | u32 | Исходный ID объекта САПФИР, НЕ номер элемента ЛИРА |
| +8 | 12 × f32 | До четырёх вершин: X/Y/Z каждой |
| +56 | 3 × f32 | Исходный вектор направления результатов |
| +68 | 32 bytes | Наименование арматурной стали |
| +100 | 32 bytes | Наименование бетона |
| +132 | 4 × f32 | `as1, as2, as3, as4`, см²/м в контрольном файле |
| +148 | f32 | Толщина, в контрольном файле метры |
| +152 | u32 | Исходные флаги; наблюдались 323 и 324 |

В проверенном варианте `flags & 0xF` даёт 3 или 4 вершины. Это наблюдаемое правило,
не обещание для любого флага. Для треугольника четвёртая тройка заполнена нулями,
это НЕ дополнительная вершина в начале координат.

Четыре площади из этой записи использовать как единственную поэлементную
огибающую пластины. Не придумывать значения трещин, поперечного армирования или
процентов, которых нет в декодированных полях.

Порядок `as1..as4` сопоставлен с предыдущей COM-выгрузкой этой модели, но нельзя
назначать этим полям глобальные «верх/низ/X/Y» без проверки ориентации. Сохранить
исходный вектор и порядок вершин как provenance; автоматический поворот не выполнялся.

## Блок определений — по 88 байт

| Смещение внутри | Тип/размер | Наблюдаемое содержание |
|---:|---|---|
| +0 | 3 × u32 | Исходные целочисленные поля |
| +12 | 32 bytes | Сталь |
| +44 | 32 bytes | Бетон |
| +76 | 3 × f32 | Исходные числовые поля |

Этот блок нужно пропустить, чтобы дойти до стержней. Его предметная семантика
не установлена; **не называть его списком расчётных сечений каждого КЭ**.

## Стержень — 160 байт + строки

| Смещение внутри | Тип/размер | Поле |
|---:|---|---|
| +0 | u32 | Исходный тип/флаг; у всех 202 объектов примера 0; смысл не подтверждён |
| +4 | u32 | ID объекта САПФИР, НЕ номер КЭ |
| +8 | 32 bytes | Сталь |
| +40 | 32 bytes | Бетон |
| +72 | 6 × f32 | X1,Y1,Z1,X2,Y2,Z2 |
| +96 | 4 × f32 | Неинтерпретированные исходные поля |
| +112 | 11 × f32 | Готовая поэлементная сводка/огибающая |
| +156 | u32 | Число следующих подробных строк |
| +160 | row_count × 44 bytes | По 11 × f32 на строку |

Порядок 11 значений сводки и каждой строки:

| Индекс | Смещение в сводке | Интерпретация |
|---:|---:|---|
| 0..3 | +112..127 | Не установлена; в контрольном файле все нули |
| 4 | +128 | as1, см² |
| 5 | +132 | as2, см² |
| 6 | +136 | as3, см² |
| 7 | +140 | as4, см² |
| 8 | +144 | perc, % |
| 9 | +148 | asw1, исходная величина; единица отдельно не подтверждена |
| 10 | +152 | asw2, исходная величина; единица отдельно не подтверждена |

В раннем исследовательском коде первые четыре поля назывались `au1..au4`.
Это **гипотеза**, не подтверждённая нулевыми данными. В нормализованном результате
их оставлять `None`/NULL, а не выдавать четыре нуля за проверенный подбор AU.

Использовать готовую сводку `+112` как огибающую. При необходимости пройти строки
и проверить, что покомпонентные максимумы совпадают со сводкой. В проверенном
коде допуск `abs(summary-max) <= 1e-4 * max(1,abs(summary))`; на всех 202 объектах
контрольного файла проверка прошла. При `row_count=0` проверить сводку и не
пытаться брать максимум пустого набора.

Для нового итогового экспорта строки **не сохранять**. Их порядок по сечениям и
признакам симметрии не проверен; нельзя обозначать `row_index` как номер сечения.
В частности, в примере чередуются ненулевые и нулевые строки — это не основание
самостоятельно назначать признаки симметрии API.

## Сопоставление ASP с моделью

### Пластины

1. Вычислить `element_id=raw_number+1` для проверенной системы нумерации.
2. Убедиться, что такой элемент есть и количество его действительных вершин равно 3/4.
3. Сравнить координаты всех действительных вершин, а не только имя/номер КЭ.
4. Для контрольной модели координаты LIR приведены к f32 и совпадают побитно с ASP.

### Стержни

У стержня в разобранном заголовке нет проверенного номера элемента ЛИРА.
Сопоставлять **по паре концов**, не по порядковому номеру и не по ID САПФИР.

Строится ключ пары точек в глобальных координатах. При поиске порядок концов
можно нормализовать сортировкой, но исходный порядок сохранить отдельно.
В существующем Rust-коде ключ — отсортированные массивы `f32::to_bits()`,
с приведением `-0.0` к `+0.0`. Численная сортировка для такого ключа не требуется,
нужна только одинаковая канонизация обеих сторон.

- Нет кандидата — ошибка соответствия ASP и модели.
- Несколько кандидатов с одинаковыми концами — неоднозначность; не брать первый.
- Уникальный кандидат — назначить его ID результату.
- Перестановка концов для поиска НЕ доказывает совпадение локальных осей арматуры.

Не вводить произвольный большой допуск, чтобы скрыть разные единицы/модели.
Для другого источника координат допустимая точность должна быть явно согласована;
при нескольких кандидатах в допуске всё равно останавливать сопоставление.

Совпадение геометрии не доказывает, что выбраны правильный вариант/дата расчёта:
два разных расчёта одной геометрии пройдут эту проверку. ASP выбирает пользователь.

## DTO и согласование с экспортом 2026

Рекомендуется разделить чтение, сопоставление и хранение:

```text
parse_asp -> source envelopes + source geometry + metadata
match_geometry -> envelopes keyed by verified element_id
write_database -> common reinforcement contract
```

Для огибающих значения `as1..as4` можно представить теми же именами и типами,
что и в экспортёре 2026. Но общность имён не разрешает придумывать метаданные:

- Не присваивать огибающей реальное расчётное сечение.
- Не присваивать произвольно symmetry=0/1, category=Total, stage=0 или номер
  варианта из API. Доступно имя варианта из ASP, но не его API enum/id.
- В прежнем writer использованы `section=0` как явный sentinel огибающей,
  `design_option=1` как import-local ID и `symmetry/category/stage=-1` как unknown.
  Это договорённость прежней БД, НЕ прочитанные значения и НЕ финальный новый контракт.
- Либо согласовать общий `scope=envelope` с такими sentinel, либо отдельный
  общий DTO/таблицу огибающих для ASP и 2026. Окончательное решение — совместно
  с владельцем экспорта 2026, чтобы потребитель не принял огибающую за сечение.
- Отсутствующие компоненты — `Option::None`/NULL, не 0. В прежней схеме
  `*_error=200` означает unavailable; для ASP это статус импортёра, не ответ COM.
- Отрицательные значения могли быть кодами отсутствия; известные/неизвестные
  статусы сохранять отдельно. Не превращать произвольный отрицательный код в
  физическую площадь и не объявлять все такие коды полностью расшифрованными.
- Для ASW1/ASW2 не предполагать см², см²/см или см²/м до независимой проверки.

## Валидация и безопасность

Точная сигнатура, ожидаемые stride, checked arithmetic, границы всех блоков,
разумные пределы счётчиков, конечность float, отсутствие повторного соответствия
одного элемента разным записям. Нет подтверждённого результата — не заполнять нулём.

Существующий importer пишет в транзакции/savepoint и откатывает весь импорт при
ошибке. Функция `import_file` открывает исходный SQLite read-only, делает Backup
в новый `.partial`, проверяет integrity/foreign keys и только потом публикует файл.
У него есть предохранитель от повторной записи в непустые таблицы армирования.

Оговорка к повторному использованию: в низкоуровневом `u32_at` из asp_import.rs
есть индексирование после предварительной проверки AspFile. Не вызывать его
на произвольном непросмотренном буфере. При выделении самостоятельного парсера
лучше сделать все primitive readers проверяемыми через `get` и `Result`.

В `AspFile.summary` статусы `unverified/raw_source_only` относятся к одной лишь
структурной проверке. Writer меняет метаданные после геометрического сопоставления.
Не путать успешный `AspFile::load` с подтверждением соответствия модели.
