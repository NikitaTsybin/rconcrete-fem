# Передача другому Codex-агенту: LIR и ASP, Rust

Дата проверки: 21.10.2026. Это практическое описание наблюдаемого бинарного
формата, **не официальная спецификация ЛИРА** и не универсальный декодер всех версий.

## Актуальное требование пользователя

Из ASP требуется **только огибающая армирования по элементу**. Структура результата
должна быть аналогична экспорту из ЛИРА 2026. Не выгружать подробные строки стержней
в итоговый контракт. Пользователь попросил пока не изменять и не собирать основное
приложение: изменения нужно внести позже одновременно с остальными требованиями.

Этот комплект — документация и копия уже существовавшего кода, не применение
отложенных изменений. Окончательное согласование схемы хранения ещё предстоит.
Нельзя выдавать огибающую ASP за результаты в конкретном расчётном сечении 2026.

## Что читать

1. [LIR_GEOMETRY.md](LIR_GEOMETRY.md) — проверенные смещения узлов и элементов,
   внутренняя индексация типов, нерешённые вопросы и алгоритм валидации.
2. [ASP_FORMAT.md](ASP_FORMAT.md) — заголовок, блоки, огибающие, сопоставление с
   геометрией, ограничения по единицам, осям и неподтверждённым полям.
3. `rust_reference/src/asp.rs` — проверка ASP и обход блоков.
4. `rust_reference/src/asp_import.rs` — существующий код разбора геометрии и
   числовых полей, сопоставления и записи в SQLite; содержит тесты.

**Не подключать существующий SQLite writer как окончательную реализацию требования.**
Это снимок прежнего кода: он дополнительно сохраняет `asp_bar_result_rows`,
`asp_section_definitions`, исходник ASP и служебные поля. Для нового приложения
переиспользовать чтение/проверки, но отделить их от записи и оставить в экспортном
контракте только огибающую. Подробные строки можно читать временно для проверки
максимумов, но не экспортировать. Полное вложение ASP — отдельное решение о
происхождении данных, не обязательная часть нового контракта.

## Копия Rust-кода

В `rust_reference` собран исходный library-crate без COM, egui и Windows API:

```toml
[dependencies]
anyhow = "1"
encoding_rs = "0.8"
rusqlite = { version = "0.40", features = ["bundled", "backup"] }
serde = { version = "1", features = ["derive"] }
serde_json = "1"
```

Это упаковка исходных модулей, **сам комплект в этом шаге не компилировался**.
В исходном приложении ранее проходили unit-тесты, а значения импорта проверены
по всему контрольному ASP. В копии находятся 8 unit-тестов модулей ASP и импорта.
По разрешению пользователя другой агент может выполнить:

```powershell
cd rust_reference
cargo test
```

Минимальное чтение заголовка в Rust:

```rust
use lira_asp_reference::asp::AspFile;
let asp = AspFile::load(std::path::Path::new("results.asp"))?;
println!("{} plates; {} bars", asp.summary.plates, asp.summary.bars);
// AspFile сам по себе читает заголовок и проверяет границы блоков.
// Поэлементные площади извлекаются кодом из asp_import.rs, а не из Summary.
```

В копии SQLite-импортёр использует `crate::asp`, соседние `schema.sql` и
`asp_import.sql`; это все его внутренние зависимости. Файлы скопированы без
изменения логики. Python не является зависимостью Rust-парсера.

## Краткий план интеграции

1. Чтение и разбор — в рабочем потоке; UI получает прогресс и итоговые owned DTO.
2. Пользователь отдельно выбирает LIR и ASP; не подбирать ASP молча по имени.
3. LIR → узлы и сырые записи элементов → проверенная таблица типов → связи.
4. ASP → огибающие → сопоставление с геометрией → валидация.
5. Запись в новый SQLite транзакцией; при ошибке не публиковать частичную базу.
6. Согласовать единый DTO/схему с экспортёром 2026. Не придумывать сведения,
   отсутствующие в ASP: номер сечения, вариант симметрии, стадию или категорию.
7. На новых файлах проверить разные типы КЭ, удалённые узлы/элементы, иной набор
   результатов и вариантов. Не делать универсальных обещаний по одному примеру.
